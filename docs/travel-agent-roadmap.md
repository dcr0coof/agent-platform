# 天气感知的出行与生活规划 Agent

状态：CLI 核心和出行工作台已在功能分支实现；天气备选、RAG、上下文预算等后续切片仍待实施。功能完成、PR 审查与主分支合并是不同状态。

## 产品目标

将当前天气工具扩展为能完成出行任务的 Agent：理解目的地、日期、预算和偏好，结合天气、路线与用户资料生成行程，在条件变化后提供有依据的替代方案。

天气是决策输入。Agent 的核心任务是规划、解释、调整与记住约束。作品集同时体现工具调度、RAG、上下文管理、可观测运行时和可用的 Web 界面。

## 典型演示

用户：“周末去杭州两天，两个人，预算 1500 元，不自驾，尽量少走路。”

1. 确认日期、出发地以及预算是否包含交通和住宿，形成可编辑的出行约束。
2. 查询预报覆盖范围内的天气，标记数据来源和获取时间；超出预报范围时明确未知。
3. 检索用户上传的攻略与官方资料，找出符合条件的候选地点，并给出原文引用。
4. 根据可用路线工具估算通勤与步行时间，生成两天行程和粗略预算。
5. 有雨时提供室内备选，用户说“不去博物馆”后立即修正约束和行程。
6. 生成行李清单与可编辑的日程草稿。保存或导出前展示结果；不自动购票或预订。

## 交付原则

- 每个 Issue 对应一条从数据、工具/API 到界面和测试的完整用户路径。
- 每个独立改动使用 feature branch 和关联 PR；每次完成的可验收提交推送远端。
- 最小闭环先交付，再逐步增加能力。所有步骤显示真实事件、错误与证据，不伪造“思考过程”。
- Provider 返回的数据、估算结果、用户提供的资料分开标注。路线估算不是交通承诺，预算不是实时报价。
- 对相同问题固定数据和策略版本进行对照评测；不凭观感宣称 RAG 或规划效果提升。

## 底层与前端

Go 保留 Agent Runtime、HTTP/SSE、工具编排，并计划增加 Context Builder 和检索接口。首个 Web 切片使用纯 Go SQLite 持久化会话、约束和运行事件，方便无需 Docker 的本机演示；一个数据库只允许一个服务进程。PostgreSQL/pgvector 在文档检索或多实例部署阶段评估迁移。当前取舍见 [ADR 0001](adr/0001-local-trip-workspace.md)，运行说明见 [工作台文档](trip-workspace.md)。

Web 使用 Vue 3 + TypeScript：左侧资料和出行会话，中间行程与对话，右侧地图、证据和运行详情。普通用户优先看到结果与可编辑约束，技术面板按需展开。

地图、路线和地点信息使用可替换的 Provider；选择供应商前核对覆盖、许可、费用和凭证要求。在用户尚未配置服务时展示明确缺失状态，演示数据必须标记，不能冒充实况。

## RAG 与上下文

资料保留来源、版本、日期和页码/段落位置。先建立向量检索基线，再实验关键词+向量融合与重排。旅行时效信息优先读取标注时间的工具结果；攻略只作为参考证据，不把旧营业时间当作实时事实。

Context Builder 将系统规则、用户确认的约束、最近完整回合、检索证据和工具结果纳入预算。完整历史单独保存；摘要可追溯、用户纠正优先，不把临时要求写成永久偏好。

## 暂不纳入首版

自动购买或预订、自动发送消息、银行支付集成、保证最低价、医学建议、通用多 Agent 平台、微调、自研向量库和复杂 OCR。天气变化后的持续监控需单独设计用户订阅与通知权限，不能默认长期跟踪用户位置。

## 验收与作品集材料

覆盖：预报不可用/超范围、同名地点、过期攻略、资料无答案、预算缺项、行程冲突、用户修改约束、检索注入、跨工作区隔离、取消与恢复。

发布材料包含真实 Demo、README、架构与数据模型、检索和上下文对照实验、失败案例、每阶段 Issue 与 PR。对外演示使用公开或自制资料，并设置访问控制、调用额度与上传限制。
