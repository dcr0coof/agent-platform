# 项目审查与优化记录

审查日期：2026-09-05。范围包含全部 Go 源码、测试、模块依赖、配置、README、Git 忽略规则及 `.hermes/plans/` 下的两份历史规划。历史规划保持原样，本文件记录当前状态和本轮修正。

## 项目处于什么阶段

这是一个完成核心链路的 Go CLI 原型，处于历史规划的 Phase 0 与天气工具接入阶段。已经具备明确的 `Client`、`Tool`、`Memory` 接口和易于替换的模型测试桩，适合继续学习与扩展。实际实现直接使用 `net/http`，仅依赖 `yaml.v3`；规划中的框架、数据库、Redis、队列和前端均未落地。

原有测试全部通过，但主要验证正常路径：没有天气 HTTP 测试、没有 CLI 测试，也未覆盖工具链被窗口裁剪、失败后继续对话、并发调用、HTTP 状态和非正常模型响应。现阶段主要问题是正确性与接口边界，缺少证据支持全面重构或性能优化。

## 已完成修正

| 模块 | 原问题及影响 | 本轮处理 |
| --- | --- | --- |
| 记忆窗口 | 按消息条数截断，可能只保留 tool 结果而丢失对应 assistant 调用 | 按完整用户回合淘汰，保留最近的超长回合及系统提示词 |
| 记忆所有权 | 浅复制 ToolCalls，调用方能修改历史内部数据 | 输入、输出均复制切片；记忆读写加锁 |
| Agent 状态 | 请求失败或迭代耗尽后残留半轮消息 | 本轮使用局部消息，成功后提交，失败保留旧历史 |
| Agent 并发 | 同一 Agent 多个 Run 可能交叉读写会话 | 同一会话串行执行，等待可取消；提供串行 Clear |
| 工具调用 | 丢失 assistant 同时返回的文本；nil 响应可导致 panic | 保留文本、验证调用 ID/类型，拒绝空响应，隔离工具 panic |
| LLM HTTP | 忽略 HTTP 状态；错误变成 JSON 解析异常；无限制读取 | 检查状态并限制响应体，保留取消错误链，拒绝截断或过滤后的回答 |
| LLM 序列化 | 零温度与空工具内容被省略；尾斜杠产生错误路径 | 明确发送 temperature 和 content；规范化 URL |
| 天气网络 | 声明 gzip 却未解压；旧域名写死，密钥放查询串 | gzip 兼容处理、专属 Host 配置、头部鉴权、状态及大小限制 |
| 天气参数 | 非法 type 静默回退为实况；空城市进入请求 | 发请求前校验；拒绝缺少天气数据的响应 |
| 计算器 | `!1`、`^1`、`&1` 被错误接受 | 一元运算符白名单；拒绝非有限结果；表达式上限 4096 字节 |
| 注册表 | map 遍历使工具定义顺序变化；有两个空测试 | 按工具名排序，替换为实际顺序回归测试 |
| 配置 | 拼写错误被忽略；非法数值进入运行时；摘要虚假启用 | 严格字段与单文档解析、数值/URL 校验；摘要关闭且拒绝静默启用 |
| CLI | 配置路径写死，扫描失败静默退出，缺少整轮超时 | 增加 -config、-timeout，改善 Ctrl+C / EOF / 长输入；提示词匹配可用工具 |
| 工程文档 | README 与实际功能不符，无 CI | 完善运行说明、本报告和 Windows/Linux CI；整理直接依赖声明 |

回归用例在修复前复现了历史截断、切片别名、HTTP 429 错误信息丢失、零温度与空内容遗漏、URL 双斜杠、天气 gzip 解析失败，以及计算器非法运算符和溢出。修复后这些用例通过。

工具定义顺序稳定、历史引用释放等属于小范围工程改进；本轮没有做性能基准测试，不宣称吞吐量或成本提升百分比。

## 外部 API 核对

和风天气官方说明旧共享域名自 2026 年起逐步停用，应使用账号专属 API Host。本轮迁移连接配置，继续使用现有城市版天气数据格式。参考：[API Host](https://dev.qweather.com/en/docs/configuration/api-host/)、[请求与 gzip](https://dev.qweather.com/en/docs/configuration/api-config/)、[城市查询](https://dev.qweather.com/en/docs/api/geoapi/city-lookup/)。

历史规划中的服务价格、免费配额、上线成本和商业化时间表均应视作当时假设，本轮没有重新核算，不能直接用作预算。规划中的“10 个 Pro 用户覆盖大部分成本”与其每月 400～900 元估算也不完全一致：290 元不足以覆盖该范围，需要按实际用量重新测算。

## 运行约束

`max_messages` 是消息条数软目标，不是严格容量或 token 预算。单个长回合保持完整，因此可以超限；一轮模型调用数由 `max_iterations` 限制。更严格的上下文控制应在构建请求时做 token 预算和整回合淘汰，保留当前回合并对超大工具输出做摘要。

失败回合不进入历史不等于事务回滚。工具可能已经执行，未来增加发消息、记账或写数据库工具时，需要明确幂等键、执行记录和重试语义。本轮不添加自动重试或并行工具执行，现有工具接口不能声明副作用和依赖关系。

同一 Agent 表示单个会话，不应被不同用户共享。BufferMemory 本身可并发读写，但多步业务操作仍应通过 Agent；例如运行期间直接调用 mem.Clear() 不能代替 ag.Clear() 的串行语义。

工具应主动检查 ctx；Go 无法安全强制终止不响应取消的自定义工具。提示词要求把工具输出当作数据只是行为引导，未来具备敏感权限时还需要在工具执行层实施访问控制。

## 后续优先级

1. **完成真实 CLI 验收。** 配好模型 Key、天气 Key 与专属 Host，验证普通对话、连续天气追问、模型额度错误与工具异常。记录请求时长、调用次数、token 用量，建立成本和可靠性基线。
2. **实现最小 HTTP 对话服务。** 先加非流式接口、独立会话 ID、请求取消和有限并发；明确错误格式与会话生命周期。之后再加 SSE 和断线处理。
3. **设计持久化和上下文预算。** 确定哪些用户事实值得保存、历史保留多久、用户如何清除数据，再选择存储。摘要应有明确触发机制和降级路径。
4. **补齐场景工具。** 天气同名城市消歧、短时缓存；有实际需求后，再加幂等重试和可并行的只读工具调度。写入工具同步设计授权与审计。
5. **在服务稳定后接小程序。** 先完成天气场景闭环，再评估健康记录、管理后台和多租户。计费应基于已计量的实际成本。

原有接口分层足够支撑上述迭代。当前保持小依赖和简单组装，可降低个人开发维护成本；出现具体规模要求或重复逻辑后再引入框架、缓存和消息队列。
