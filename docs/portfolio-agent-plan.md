# 作品集升级计划：可追溯的知识研究 Agent

状态：待讨论的方案，不代表已实现。日期：2026-09-05。
后续用户将主场景调整为天气关联的出行与生活规划，执行路线以 [出行 Agent 路线](travel-agent-roadmap.md) 为准；本方案中的 RAG、上下文、证据和评测设计继续复用。
目标岗位：AI 应用 / Agent 开发。保留 Go 核心，兼顾可展示的 Web 产品。

## 1. 产品定位

建议以“技术资料与项目决策研究工作台”为场景：导入个人笔记、项目设计文档、技术材料，Agent 根据证据回答问题、比较方案、识别版本冲突，并生成可修改的研究笔记。

示例任务：上传项目的初版计划和最新设计，询问“数据库方案改变了什么？在每周 10 小时、单人维护的约束下推荐哪个方案？引用原文，资料不充分的部分单独列出”。继续修改约束，检验 Agent 是否正确更新结论和记忆。

作品集核心卖点：证据可追溯、上下文可检查、质量有评测。新意来自完整产品与工程实现；不宣称提出新的 RAG 算法。天气和计算器保留为工具示例。

## 2. 当前缺陷

| 层次 | 当前代码 | 对作品集的影响 |
| --- | --- | --- |
| 产品 | CLI + 通用问答 + 简单工具 | 缺少稳定的用户场景和可展示成果 |
| Runtime | Run 内执行模型和工具循环，只返回最终字符串 | 缺少运行事件、状态恢复、成本统计、任务级评测 |
| 检索 | 无解析、分块、embedding、检索、引用 | 无法回答私有资料问题，尚不具备 RAG |
| 上下文 | 按完整回合保留消息；max_messages 为软目标 | 不知道请求的 token 占用；长回合和工具结果可能超出模型窗口 |
| 记忆 | 进程内历史；无摘要和持久化 | 重启丢失，无法区分任务约束、用户偏好和资料事实 |
| 模型接口 | Response 只有 Content 和 ToolCalls | 缺少流式事件、usage、provider 能力与错误分类 |
| 前端 | 无 | 无法直观呈现检索、证据和执行过程 |
| 评测 | 已有单元与本地 HTTP/CLI 集成测试 | 能证明程序行为，不能证明回答正确率和检索质量 |

已有的 Client / Tool / Memory 分层可以继续使用；在接缝处扩展，避免一次性重写。当前失败回合不提交聊天历史，但未来需要单独保留运行失败事件，以支持诊断和恢复。

## 3. 三个核心展示点

### A. 证据驱动的回答

答案中的关键结论关联文档版本、页码或段落；点击引用打开原文。资料冲突时并列展示双方证据，注明适用时间和条件，不自动把最新文档视为绝对正确。没有足够证据时指出缺口。

### B. 可检查的上下文管理

展示每次模型请求实际使用的历史、证据、任务约束和摘要，各部分 token 估算、保留或淘汰原因。允许用户固定约束、修正记忆、切换文档版本。

这里展示输入组成和可观察的执行事件，不要求展示模型内部思维链。token 估算与服务返回的 usage 分开标注，避免伪精确。

### C. 可复现的实验与运行记录

同一问题可对比“向量检索”“混合检索”“混合检索 + rerank”的命中证据、答案、耗时和成本。记录数据集、索引、prompt 和模型版本；历史事件回放与重新调用模型分开，重新运行不承诺逐字一致。

## 4. 建议架构

```text
Vue 3 + TypeScript 工作台
              │ HTTP + SSE
Go API：工作区 / 文档 / 会话 / 运行 / 事件
              │
Agent Runtime ─ Context Builder ─ Model Provider
       │              │
Tool Executor     历史 / 任务状态 / 摘要 / 证据
       │
Retriever：关键词 + 向量 → RRF → 可选重排
       │
PostgreSQL + pgvector
       ↑
导入任务：文件 → 解析 → 结构分块 → embedding → 原子激活索引版本
```

技术选择：

- Go 保留运行时、接口、任务调度和检索编排；使用标准库 HTTP 起步，SQL 迁移管理数据库结构。
- PostgreSQL 同时存业务数据和向量。小规模先精确向量检索，测得需要后再增加 HNSW；对比延迟与召回损失，关注工作区过滤后的召回。
- 关键词分支先用 PostgreSQL 全文检索，中文必须验证分词与中英混合技术词的处理。全文检索评分不冒称 BM25；若增加 BM25，明确实现或搜索组件，单独实验收益。
- 前端采用 Vue 3 + TypeScript + Vite，优先复用原规划中的 Vue 经验；使用现成可访问组件与代码高亮、Markdown 渲染，定制研究工作台布局。
- 初期 Go 单服务 + PostgreSQL + 本地文件目录，Docker Compose 启动。不默认增加 Redis、微服务或额外向量数据库。
- 文档解析封装适配器：先 Markdown/TXT 与可提取文字的 PDF；后续有需求再引入 Python 解析 worker、扫描件 OCR、复杂表格。
- embedding 与 reranker 通过可替换接口接入，选择适合中文及中英混合资料的模型，用评测决定最终版本。升级模型维度或分块策略需要新建索引版本。

## 5. RAG 设计

### 文档导入

链路：上传 → 大小/类型校验 → 内容哈希 → 解析 → 分块 → 批量 embedding → 索引构建 → ready。

保留 document_id、version_id、chunk_id、标题层级、页码/段落位置、原文偏移、内容哈希、embedding 模型及分块版本。状态包括 queued、processing、ready、failed，可重试。文件去重以工作区和内容哈希为边界。

切块以章节、段落、列表、代码块为边界，再使用 token 上限拆分。初始范围可试 400～800 token，但作为待评测参数。子块用于召回，父段落用于补充语境；标题与章节路径附在检索文本中，引用仍定位原文。

索引更新完成后才切换 active version，避免半批新旧向量混用。删除和版本切换同时影响检索、缓存及引用展示；历史运行引用保留对应版本标识并标记资料已删除或失效。

### 查询链路

问题与必要的对话约束 → 可选查询改写 → 工作区/文档版本过滤 → 关键词和向量检索 → RRF 融合 → 去重 → 可选 rerank → 按 token 预算打包证据 → 带引用生成。

初始可实验各分支召回 20 条、合并后重排、最终选择 5～8 个证据块；这些不是固定最佳参数，须与直接向量召回对照测试。

服务端核验引用 ID 是否来自本次证据集及其原文位置；引用存在不等于能够支持结论，后者需要专门的支持度评测与人工抽检。不把相似度当成“答案正确概率”。

### Agentic RAG

把 search_documents、read_section、compare_versions、save_note 暴露为受约束的工具。简单问题只检索一次；证据不足时允许改写查询或读取相邻段落；比较任务可以分开查找双方证据。

按检索次数、模型调用次数、token 和耗时限制任务。检索仍无足够支持时输出缺口或请求补充资料，不靠无限循环补救。RAG 是证据获取能力，上下文管理负责决定哪些证据进入下一次调用。

## 6. 上下文与记忆设计

将持久化历史与每次发送给模型的上下文分开：Session Store 保存完整历史；Context Builder 生成受预算约束的请求。继续保持工具调用与结果配对完整。

| 信息 | 保存内容 | 使用规则 |
| --- | --- | --- |
| 系统规则与工具定义 | 身份、边界、工具 Schema | 每次计入输入预算，不混入外部文档指令 |
| 当前任务状态 | 目标、已确认约束、未完成项 | 结构化保存，当前任务优先 |
| 最近完整回合 | 原始对话与工具结果 | 按预算选择，保留必要指代上下文 |
| 检索证据 | 原文片段及来源 | 按相关性、版本与预算动态加载 |
| 历史摘要 | 旧回合的压缩信息和来源消息 ID | 可追溯；用户纠正后更新，不冒充原始事实 |
| 长期偏好 | 用户明确表达或确认的稳定偏好 | 按工作区隔离，可查看、编辑、删除 |

可用输入预算 = 模型窗口 − 输出预留 − 工具/推理等供应商要求的预留 − 安全余量。工具 Schema、历史和证据均计入；精确 tokenizer 不可用时采用保守估算并记录误差。

压缩顺序：减少重复证据和冗长工具内容 → 将完成的旧回合压成带来源的摘要 → 淘汰低相关材料。原始内容仍保存在数据库或文件中，以引用按需读取。若当前任务的最低必要上下文仍超限，应明确失败或拆分任务。

摘要、资料内容和工具返回均作为带来源的数据，不能提升为系统规则。避免自动把一次临时要求写成永久偏好。长期记忆候选先展示给用户确认；同一事实发生修改时保留替代关系。

关键测试：长对话后的指代、用户更正旧约束、重复工具输出、摘要偏差、文档内恶意指令、跨工作区隔离、删除后不再召回。

## 7. Agent 底层设计

- Run 状态：queued、running、waiting_for_approval、completed、failed、cancelled；Step 记录检索、模型及工具执行。
- 输出事件：run.started、retrieval.finished、tool.started、tool.finished、message.delta、run.completed、run.failed。事件含 run_id、step_id、递增序号和时间。
- SSE 用于状态和文本增量，取消使用独立 API；断线后按事件序号续读，不能意外启动第二次运行。模型真正 token 流与先显示步骤状态分阶段实现。
- 独立会话互不阻塞，同一会话串行；只对明确独立的只读工具做有界并发。工具元信息区分只读/写入、超时、审批与幂等策略。
- checkpoint 保存可恢复状态、工具输入及结果引用；写入工具已执行但未确认结果时标为待核对，不能直接重放。首版审批仅用于写入研究笔记等具体动作。
- Usage 记录模型报告的输入/输出 token，另记估算值、检索与生成耗时、模型调用次数。成本依据有版本的价格配置估算，不能假装是账单。
- 全链路携带 trace_id；生产日志默认不记录密钥和完整私人文档。作品集演示使用公开或自制资料。

## 8. 前端展示

优先实现三栏研究工作台：左侧资料/会话，中间任务与回答，右侧可切换“原文证据 / 执行过程 / 上下文”。窄屏折叠成抽屉，不把全部开发信息堆给普通用户。

核心页面：

1. 工作区与资料库：拖拽上传、解析进度、失败重试、版本标签、文档预览。
2. 研究工作台：流式回答、取消、引用定位、答案保存、资料冲突卡片。
3. 上下文与记忆面板：预算分布、实际选中的材料、固定约束、记忆修正与删除。
4. 运行详情与评测：步骤时间线、重试和错误信息、策略对比；高级内容折叠显示。

首版 Markdown 引用精确到段落，PDF 引用先到页码，版面坐标可靠后再做区域高亮，避免假装实现像素级定位。Markdown 渲染需清理不可信 HTML。

展示内容应为真实检索结果与事件，不使用伪造的“思考中”长文充当推理过程。

## 9. 评测从第一阶段开始

先准备约 30 个手工标注问题，后扩展到 80～100 个，涵盖事实、专有词、中英混合、跨文档、多轮约束、版本冲突和无答案问题。将开发集与最终测试集分开。

标注问题、可支持结论的原文、允许答案及无答案原因；不只依赖模型合成的 QA。

对比路线：向量检索基线 → 混合检索 → 加重排 → 加按需二次检索。上下文对比：消息窗口 → token 预算 → token 预算 + 结构化任务记忆。

指标包括检索 Recall@k/MRR、引用 ID 有效率、结论证据支持度、无答案误答率、多轮约束保持、任务完成率、P50/P95 耗时、调用数和 token 消耗。LLM 评分只作辅助，保留人工抽检与争议样本。

质量指标先测基线再定目标，不预先承诺提升百分比。工程性验收包括引用 ID 可解析、权限隔离、取消终止后续调度、断线续读不重复执行工具。

## 10. 分阶段交付

| 阶段 | 交付 | 验收 | 估算 |
| --- | --- | --- | --- |
| P0 场景与基线 | 数据样例、30 个评测问题、界面草图、数据模型和事件协议 | 演示任务和评测口径明确 | 8～12 小时 |
| P1 全栈闭环 | Go API、工作区/会话、持久化、Vue 工作台、SSE 状态 | 浏览器发起任务、取消、重启恢复历史、查看工具事件 | 18～25 小时 |
| P2 可引用 RAG | 导入 MD/TXT/文本 PDF、分块、embedding、检索、引用 | 从资料回答并定位原文；无答案用例进入评测 | 25～35 小时 |
| P3 上下文与检索改进 | token 预算、摘要、任务状态、混合检索、重排实验 | 长对话约束测试；输出策略对比结果 | 25～35 小时 |
| P4 作品集亮点 | 版本冲突展示、受限二次检索、运行回放、笔记审批保存 | 跨文档完整演示，前端展示真实证据和过程 | 20～30 小时 |
| P5 交付打磨 | 部署配置、访客演示与额度限制、评测报告、架构说明、演示视频 | 新环境按 README 启动，演示可复现 | 12～18 小时 |

合计约 108～155 小时，是范围估算。若延续原规划的每周 10～15 小时，约需 8～16 周，另留学习与外部 API 调试余量。P2 结束就是能演示的第一版；预算不足时先推迟 P4 中的版本冲突与审批，保留引用和评测。

候选目录：cmd/server、internal/api、internal/run、internal/context、internal/ingest、internal/retrieval、internal/store、web、evals。按阶段出现真实职责后创建，不预先铺设空壳。

## 11. 范围边界

首版不同时做小程序、SaaS 计费、多人协作、图谱数据库、模型微调、通用多 Agent 编排或自研向量数据库。OCR 与复杂 PDF 排版后置。每个扩展需对应具体用例及评测收益。

后续可选：GraphRAG（确有实体关系/全局归纳问题时）、MCP 工具适配（确需外部工具互通时）、多 Agent 并行研究（存在独立子问题且测得成本收益时）。协议和框架本身不作为新意指标。
